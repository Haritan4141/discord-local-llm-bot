# 音楽生成の進捗表示

## 実装範囲

YuE2 / ComfyUI ACE-Stepの進捗受信、工程・経過時間・推定残り時間表示、成功時の所要時間集計を追加する。Botのキュー、曲の生成条件、安全上限、音声添付、アイドル時のVRAM解放方式は変更しない。

## 設計上の制約

- YuE2のABC・音楽トークン数は可変長の安全上限に対する値であり、曲全体の完成率として表示しない。
- KSamplerの固定ステップには工程内の進捗率を表示する。初回も速度が安定すれば、この工程の残り時間を推定できる。
- 完了までの目安は同じサーバー・モデル・workflow設定・指定秒数・観測キャッシュ状態の成功実績が3件以上ある場合だけ範囲で表示する。実績不足は同条件・同工程の完了件数、予測超過はその理由を明示する。
- 計測にプロンプト・歌詞・Discordユーザー情報は保存しない。履歴は件数を制限したローカル集計のみ。
- 同じDiscord返信を約5秒以上の間隔で更新する。イベント受信自体は返信を書き換えず、既存のポーリング処理から直列に更新して完了・エラーを上書きしない。
- WebSocketは進捗専用。接続失敗・切断時も生成を再送信・中断せず、従来のhistoryによる結果取得を続ける。
- 既存の自然終了、安全上限警告、音声添付、Botトークンによる長時間返信方式を保持する。
- BLUEのComfyUI・モデル・Firewallは変更しない。本番Bot以外のBLACKサービスに触れない。

## 表示例（数値は例）

```text
🎵 YuE2で音楽を生成中です（長さの目安: 120秒 / 安全上限: 360秒）
工程: 音声生成（20 / 32ステップ・62%）
経過: 1分10秒（生成処理の開始から）
完了目安: 実績を収集中（同条件: 2/3件完了）
この工程の残り: 約30秒〜1分0秒（推定・保存/送信時間は別）
※ 曲の長さは目安です。％は表示中の工程内の進捗で、曲全体の完成率ではありません。
```

工程はモデル準備→作曲→曲構成→音声生成→音声変換→保存/取得へ移る。ComfyUIの実行順やキャッシュによって一部工程が省略・短縮されるため、固定の全体％は作らない。ABC/音楽トークンが安全上限に対して何％かは表示しない。

## 推定と通信の詳細

- 固定ステップの速度推定は3点以上・2秒以上の実測から計算。直近の通知が古い場合は表示しない。
- 完了目安は同一設定の工程開始からDiscordへの音声添付完了までの実績から算出。過去最小値の70%～最大値の130%を基に経過分を差し引き、5秒単位に丸めた幅で表示する。範囲を超過した場合は「過去の実績からの予測時間を超過」と表示し、架空の残り0秒や再計算中とは表示しない。
- `estimateStatus()` は実績不足・予測可能・超過・情報不足を区別する。既存の `estimate()`、集計キー、保存形式、最低3件の条件は変えない。3件目の正常完了後、次の同条件の生成から予測する。
- 通知が古い／切断中は「進捗通知の更新待ち」、条件未確定は「サーバーの実行情報待ち」とし、実績0件と混同しない。途中で通信断があった生成は再接続後も完了予測を表示せず、理由を明示する。結果確認・音声取得／送信は「最終処理中」とする。独立ACE APIは従来どおり完了目安非対応。
- キャッシュ済みノード一覧の一致を条件とし、冷間/温間を時刻だけで決めない。ただしGPU競合やモデル内部の再ロード等を完全に予測するものではない。
- 時間記録は正常に音声添付が完了し、開始・キャッシュ通知を受け取れ、途中の通信断もない場合のみ。失敗・タイムアウト・不完全な通知から学習しない。
- `data/music-timings.json` は設定をハッシュ化したキー・工程識別子・所要時間だけ。最大64設定・各工程12件を保持し、ファイル破損/書込失敗は生成へ影響させない。削除すれば計測実績だけを初期化できる。
- 約5秒の最短間隔で同一メッセージを編集する。通常は既存の2秒ポーリングに合わせ約6秒間隔となる。Discord側の制限や通信時間により遅れる場合がある。
- WebSocketはHTTP送信前に接続を試み、同じ固有client IDを`/prompt`に渡す。別prompt IDの通知は無視し、切断時は再接続する。最初の接続待ちは最大約2秒。history取得は従来どおり継続する。
- 進捗を受信できない間は「詳細進捗の更新待ち」と経過時間を表示する。これは生成停止を意味しない。
- 独立ACE API（`MUSIC_BACKEND=ace`）は工程・ステップを取得できないため待機/生成中と経過時間のみ。ComfyUI ACE-Stepでは8ステップの工程内進捗を取得可能。

## 本番反映手順

1. 最新mainと競合しないことを確認し、テスト後にPRをmainへマージ。
2. BLACKのAlias/IP/hostname、Bot管理GUI、生成Queue/Discord応答のidleを確認。
3. `.env`、保存済み参照画像、既存lock差分を保護してfast-forward pull。
4. 全テストと依存関係を確認後、既存GUI経由でBotだけを再起動。
5. 起動ログ、保存データ、YuE2への進捗接続を再確認。実曲の最終表示は次のユーザーテストで確認する。

この変更はスラッシュコマンド定義を変更しないため、コマンド再登録は不要。

## 自動テスト

`npm test` で既存機能と併せて検証する。進捗の対象prompt ID照合、先行イベント、binary/不正メッセージ、切断/再接続、localhost実WebSocket・接続拒否・接続タイムアウト、編集の間隔/直列化、完了後の更新停止、historyフォールバック、可変長部分での％非表示、工程内ETA、実績3件後の完了ETA、永続化・破損・容量制限をカバーする。

APIキーを使ったOpenAI呼び出しや実曲の再生成は自動テストでは行わない。別タスクの `/draw` 修正も最新mainとの統合後に回帰テストする。
